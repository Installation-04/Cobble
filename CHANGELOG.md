# Changelog

All notable changes to this project are documented here.
Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning follows [SemVer](https://semver.org/).

## [Unreleased]

### Added
- v0.3: **reviewer agent and per-task time limit** (ADR 0024). Optional per project (off by default because it costs tokens; `review_enabled` on the projects API, a switch in the Agents tab): when CI is green a `reviewer` model (through the cost router, `local only` honoured, cost shown under role `reviewer`) reads the task's acceptance criteria and diff and answers approve or request changes with concrete issues. Approval merges as before; requested changes start another attempt like a red CI (issues added to the worker's prompt, escalation and `COBBLE_MAX_ATTEMPTS` apply); an unreadable verdict is asked again once, then approved with a recorded warning. New task state `review` ("In review"), events `task.review_started` and `task.reviewed`, the verdict and issues in the task drawer (FR/EN). New `COBBLE_TASK_MAX_SECONDS` (default 2700, `0` = off): a task over its wall-clock limit, all attempts together, is stopped and failed with `task_timeout` (explained in the drawer, event `task.timeout`); the project goes on. Migration `0019`. Docs in `docs/{fr,en}/costs-agents.md`.
- v0.3: **questions from agents to the user** (ADR 0025). An agent can stop and ask instead of guessing: it prints `[cobble:question] {"question": "...", "choices": [...]}` (or writes `.cobble/question.json`, which the runner turns into that line). The agent-service stops the container at once, keeps the committed work on the branch and reports the run as `question`; the scheduler stores it in the new `task_questions` table (migration `0020`) and parks the task as `waiting_human`: no failure, no attempt used, no agent slot, no tokens, no timer running. The Agents tab shows a badge with the open questions and the task drawer lets you answer (suggested choices or free text) or skip; the task then resumes the same step with your answers in its prompt. At most 3 questions per task, texts capped at 2000 characters. API `GET /api/v1/projects/{id}/questions`, `POST .../questions/{qid}/answer` and `.../skip`; events `task.question` and `task.answered`. Docs in `docs/{fr,en}/agents.md`. Notifications outside the app stay for v0.4.
- Install straight from GitHub (ADR 0022): `curl -fsSL https://raw.githubusercontent.com/Installation-04/Cobble/main/installer/install.sh | sudo bash` installs the latest release (`cobble.tar.gz` of the GitHub release). New options `--version vX.Y.Z`, `--ref <branch|tag|sha>` (GitHub archive built from source, with a "not a verified release" warning), `--no-verify` (unsafe) and `COBBLE_REPO=owner/name` for forks. A downloaded tarball is saved to a temporary file and its SHA-256 (`<url>.sha256`) is checked before anything is unpacked; a mismatch, a missing checksum or an unpublished release stops the install with a clear FR/EN message (`--ref main` is suggested when no release exists). When the tree has `core/compose.release.yml`, the installer, the systemd unit and `cobble` add it to every compose call so the published images are pulled instead of built. `cobble update` accepts `--latest`, `--version`, `--ref`, `--source` and `--no-verify`. Docs in `docs/{fr,en}/install.md`.
- v0.3: **release pipeline** (ADR 0023). Pushing a `v*` tag runs `.github/workflows/release.yml`: it builds the core images (`api`, `worker`, `module-manager`, `ui`, `fake-llm`), pushes them to GHCR with source labels, generates `core/compose.release.yml` (every built service pinned by digest, `scripts/make_release_compose.py`) and creates the GitHub release with `cobble.tar.gz`, `install.sh` and their `.sha256` files. `workflow_dispatch` with a tag name is a dry run that publishes nothing. Module images are still pinned in the manifests before tagging. Procedure in `docs/{fr,en}/releasing.md`.
- v0.3: **"Explain me" mode** (ADR 0017). A project can turn on, in the Demo tab (or `explain_mode` on the projects API), a plain-language summary written at each milestone: what was built and why, in your language, shown on the milestone card and included in the Markdown report. Off by default because each summary costs a few tokens: it goes through the cost router with the `reviewer` role and is counted in the project costs. `POST /api/v1/projects/{id}/milestones/{ref}/explain` writes or rewrites one on demand. Migration `0016`. Docs in `docs/{fr,en}/demo.md`.
- v0.3: **mockup variants** (ADR 0018). Optional per project (off by default, Plan tab): the planner proposes 2 or 3 different mockups (title, summary, ASCII wireframe) for one short planner call, the user compares them side by side and picks one before the plan; the chosen mockup is added to the plan prompt, and plan generation waits for the choice while the option is on. Wireframes are stored and shown as plain text only (never markup). Migration `0017` (`projects.mockups_enabled`, `mockup_variants`), `GET`/`POST /api/v1/projects/{id}/mockups…`, job kind `mockups`. Docs in `docs/{fr,en}/mockups.md`.
- v0.3: **run the local benchmark from Settings** (ADR 0019). Settings → Models → Local benchmark has a "Run benchmark" button: tick the models (local ones by default; paid ones only on purpose), follow the progress (task x of 8), and the results refresh when it ends; a failure such as `sandbox_unavailable` is explained there in French and English. Admin-only API `POST /api/v1/models/benchmarks/run` (409 `benchmark_running` if a run is going, 422 `benchmark_paid` without `allow_paid`) and `GET /api/v1/models/benchmarks/status`; the run is a `benchmark` job on the existing Redis job stream, its state lives in Redis (no migration). The CLI and the job share one runner (`cobble.benchmark.job`); a sandbox or model failure no longer stores a misleading score.
- v0.3: **agent benchmark** (ADR 0020). Five reference projects (`todo`, `blog`, `invoicing`, `dashboard`, `bot`) with frozen FR/EN specs, hidden acceptance tests kept out of every generated repository, and reference solutions plus mutation checks proving the tests are satisfiable and discriminating (`make bench-check`). `make bench` runs them through the API with a per-project cap and a total budget, runs the hidden tests on the generated code and writes JSON and Markdown (FR/EN) reports with success rate, average cost, tokens, duration, escalations, fallbacks and "no project exceeded its budget"; it refuses to start without explicit confirmation, credentials and a real model connection. `make bench-dry-run` tests the runner on a simulator. The paid run itself is still to be done by the owner. Docs in `docs/{fr,en}/bench.md`.
- v0.3: **local package cache** (ADR 0015). Two optional catalogue modules, `verdaccio` (npm) and `devpi` (PyPI), each a read-through cache with no web page, a data volume, resource limits and a health check, providing `package-cache` plus `npm-cache` / `pypi-cache`. They are in no starter pack and are covered by the install/uninstall matrix test. They are not wired to the agent runners yet (needs optional links in the resolver and the agents' proxy allow-list: described in the ADR). Docs in `docs/{fr,en}/modules.md`.

### Changed
- v0.3: **electricity of local models, per-task caps, model-aware estimate** (ADR 0021). Set a price per kWh and a power draw (Settings → Models, `cobble costs`, `PUT /api/v1/settings/costs`): calls to local models record an estimated electricity cost (migration `0018`), shown on its own line in the Costs tab and the report, counted in the spent amount and budget only if you enable it (an estimate, not a measure). A task now has its own cost cap (default 3x its estimate, at least 0.05 USD; 0 turns it off): over it the call is refused (`task_budget_reached`), the project keeps running. A call already in flight can still overshoot by one call. The plan estimate now prices each role at the first model of its route (free and local = 0).
- v0.3: **up-to-date prices and free tiers** (ADR 0013). The last price seen of each model is remembered (migration `0014`, `model_prices`; the gateway stays the only source) and a change is shown as a warning for 14 days in Settings → Models → Prices and in the Costs tab, without ever reordering your routes; `GET /api/v1/models/prices` and `cobble models prices`. Free tiers (zero price, or OpenRouter `:free` models; local models excluded) get a "free" badge and their calls are counted as free in the costs report (`free_calls`). A model that answers 429 is now tried after the others for 30 s, doubling up to 10 min. Provider terms and rate limits are documented as the owner's responsibility.
- v0.3: **end-of-project report** (ADR 0014). New "Report" tab in the project and `GET /api/v1/projects/{id}/report`: what was built (milestones, tasks done / failed / escalated), time span, real cost against budget and plan estimate, the savings counter, cost per model and role, fallbacks and tokens. `?format=md` (or the "Download as Markdown" button) gives it as a Markdown file in the user's language (fr/en). Computed when read, nothing stored, no schema change.
- v0.3: **crash recovery** (ADR 0016). A planner job (interview reply, spec, plan and each plan retry) stores the model's answer in the database before using it; a job replayed after a worker restart reuses those answers instead of calling the model again, so nothing is paid twice. Migration `0015`. The scheduler already resumed its tasks from the database; the ADR documents that and lists the remaining gaps.
- v0.3: **crash recovery, remaining gaps closed** (ADR 0016). (1) A job whose handler crashes (a bug) is no longer dropped: it stays pending and is retried after 30 s, up to 3 deliveries, then it is parked in the dead-letter stream `cobble:jobs:dead` (job, error, delivery count; `redis-cli XRANGE cobble:jobs:dead - +`) and the project shows a translated "job crashed" banner. A job that keeps killing its worker is parked too, without running a fourth time. (2) The start-up reclaim no longer steals a live second worker's jobs: a restarted worker takes back its own jobs at once (its consumer name is its container's host name, or `COBBLE_WORKER_NAME`), another consumer's jobs only after 10 min of silence. (3) An agent run whose start was accepted by the agent service just before a crash is adopted again instead of being orphaned and duplicated: new `AgentRunner.find(marker, task_id)` and `GET /v1/runs?task_id=&marker=` on the agent-service (an older service without it keeps the previous behaviour). No schema change.
- v0.3 step 6: **local model benchmark** (ADR 0012). `cobble models benchmark` measures models on 8 coding tasks with hidden cases, running the generated code in a new module-manager sandbox (`POST /v1/sandbox/run`: throwaway container, no network, read-only, 256 MB, 1 CPU, 64 processes, killed at the time limit). Results (quality, tokens/s) are stored (migration `0013`), shown in Settings → Models → Local benchmark with a "Use as worker" button, and the best `worker` model is proposed (`--apply` to set it). Local models only unless `--allow-paid`.
- v0.3 step 5: **"local only" projects** (ADR 0011). A project can be switched, in the Costs tab (Privacy card) or with `local_only` on the projects API, to use only models served on this machine: the cost router, through which every model call passes, drops every other model from the role's chain and from escalations, and refuses the call before sending anything when none is left (`local_only_unavailable`). It fails closed: if the local models cannot be listed, none is local. Migration `0012`. Package downloads of the generated app are not covered.
- v0.3 step 4: **savings counter** in the Costs tab: what the project really cost compared with doing every call with the strongest model you configured (the first model of the escalation route), with the saved amount and percentage, or "no saving" when the project cost more, never hidden. The reference prices come from the gateway's own `/model/info` (Cobble keeps no price table); when the strongest model cannot be priced the card says it is not available. Computed when the tab is read, nothing stored, no schema change.
- v0.3 step 3: **fallbacks are visible in the Costs tab.** A call answered by a fallback model now records the first model that could not answer and how many failed before it (migration `0011`: `llm_calls.fallback_from`, `fallbacks`); the project costs report gets a `fallbacks` block and the Costs tab a "Calls answered by a fallback model" section (who answered instead of whom, calls, cost) with a hint to check the routes when more than 20 % of the calls fell back. Also fixed: a route naming a model the gateway no longer knows (for example a removed connection) now hands over to the next model instead of failing.
- v0.3 step 2: **model presets** "Économique local" and "Équilibré". One click (Settings → Models → Presets, or `cobble models preset`) fills the routes of all roles from three slots you choose (a local model, an inexpensive model, a strong model); a preset that lacks a required model is shown as unavailable and changes nothing. Models served on this machine by installed backends (Ollama) are now listed (`local` in `GET /api/v1/models`) and can be named in routes. No schema change.
- v0.3 started (explicit owner override of `PLAN.md` §18, with the v0.1 step 11 validation still owed): **per-role model routes with fallback chains**. In Settings → Models (and `cobble models route`) each role (planner, test-writer, worker, reviewer, escalation) gets an ordered list of models: the first answers unless it cannot (key refused, balance, rate limit, unknown model, service down), then the next is tried; a request the service rejects as malformed is not retried elsewhere. Migration `0010`; `GET`/`PUT /api/v1/models/routes`. New `escalation` role (unset: `COBBLE_ESCALATION_MODEL`, then the planner's chain).
- **Breaking**: the v0.1 pack (`packs/v01`, installed by hand) is retired. The agent runner and the milestone previews are now the catalogue modules `aider` (agent-service, egress proxy, Aider runner image) and `preview`, installed with `cobble modules install` (or any starter pack) and found by the core through the module-manager; the `.env.pack`, `.env.agents.core` and `.env.preview.core` files, `gen-env.sh` and the `COBBLE_AGENT_SERVICE_*` / `COBBLE_PREVIEW_SERVICE_*` settings are gone. A v0.1 pack installed by hand must be removed manually (docs/en/modules.md); nothing is migrated. Service sources moved to `services/`.
- Images that are not third-party are built by CI (`.github/workflows/images.yml`), pushed to GHCR and pinned by digest in the manifests (`scripts/pin_images.py`). Forgejo shares its API token with the hooks of modules that require `git` (`link_secrets`). New manifest field `web_ui.public: false` (reachable by the core, no route on the proxy).

### Added
- v0.2 acceptance matrix (`test_catalog_matrix.py`): the official catalogue installs and uninstalls in every order without conflict, with the real module-manager and a fake Docker; release notes and validation report in `docs/releases/v0.2.md` (not published).
- `cobble-sdk init|lint|test` (SDK CLI): scaffold a module, check its manifest, files, hooks, placeholder digests and the platform compose rules, and try installing and removing it on sample machines. `make lint` now lints the official catalogue with it.
- First-run wizard: after creating the account, the administrator is offered three skippable steps once: the machine (memory, GPU) with the recommended starter pack, a model service with an API key, and an example project (a to-do list) started in the chat. Finishing or skipping is remembered (`GET /setup/progress`, `POST /setup/complete`). French and English.
- `cobble models list|add|test|default|remove`: the same model connections from a terminal. The API key is typed at a hidden prompt or piped on stdin, never an argument.
- Settings → Models (administrators): connect a model service (OpenAI, Anthropic, OpenRouter or any OpenAI-compatible address) with an API key, test it, choose which one answers, remove it. The key is sent once, stored encrypted and never shown again; the gateway restarts in about 20 seconds. French and English.
- v0.2 started (explicit owner decision, before the v0.1 step 11 validation): `sdk/` (Apache-2.0) with the module manifest schema and validation (`cobble_sdk`), a generated JSON Schema, and tests; digest-pinned images, FR+EN descriptions and strict fields are enforced.
- `cobble_sdk.resolve`: pure dependency resolution and planning for modules. The installed set is a function of the explicitly requested modules, so installs and uninstalls converge whatever their order; required capabilities are added automatically (or a choice is requested), exclusive conflicts and cascades are reported, and a hardware-aware variant chooser is included. Property tests (Hypothesis) encode the "any order" criterion.
- `cobble_sdk.rewrite`: the platform's anti-conflict rules applied to a module's compose file (`docker compose config --format json`, no daemon needed): host ports removed, project/container/volume/network names namespaced `cobble-<id>`, shared-network access (with a unique alias) only for declared services, default CPU/memory/PID limits, labels; privileged mode, host namespaces, dangerous capabilities, stray bind mounts, external volumes/networks, `build:` and undeclared images are rejected, all violations reported together. The manifest gains `web_ui.service` and `bus`.
- Database migration `0008` for the module-manager: `modules`, `module_secrets` (encrypted, one per module and key), `module_links`, `module_events` (history that outlives a module) and the single-row `platform_state` (first-run setup flag and the modules generation counter). Tested up and down on Postgres, plus a test that fails when a model drifts from the migrations.
- The module-manager's secrets vault (`cobble.module_manager`): AES-256-GCM bound to the module and key name, versioned master keys (rotation-ready), a master key file that must be readable by its owner only, `SecretValue` that never prints itself, an encrypted `SecretStore` over `module_secrets` (the API can only learn whether a secret is set), and a log filter that masks registered secrets. New dependency: `cryptography` (Apache-2.0 or BSD-3-Clause).
- The module-manager lifecycle (`cobble.module_manager.manager`): install (record, hardware, secrets, render, up, hooks, health, link) and uninstall with rollback of the whole plan on any failure, planning against what is really running (orphans are cleaned), crash recovery, link hooks run provider first, and a `Runner` interface with a `docker compose` implementation and a fake one. Fault injection at every step shows nothing is left behind. The backend image now installs the SDK through a named build context (`sdk`).
- The module-manager service (`python -m cobble.module_manager`, step 7a): an internal HTTP API (bearer token) to list the catalogue with a per-machine verdict, preview a plan, run install/uninstall operations one at a time in the background, read an operation and see which secrets are set (never their values); progress goes to the Redis stream `cobble:modules:events`. It reads the catalogue from disk, creates its vault master key privately on first start, recovers interrupted operations at start-up, and detects the machine's RAM and GPU. It ships as the `module-manager` image target (the backend image plus the pinned Docker CLI and compose plugin) and as a `module-manager` compose service behind the `modules` profile, the only one with the Docker socket and the key volume. `scripts/dev_env.py` adds its token and paths to an existing environment without touching other values.
- The modules API for the browser (step 7b), administrators only: `GET /api/v1/modules` (catalogue with each module's fit for this machine and its state), `POST /modules/plan`, `POST /modules/operations` (202, one at a time), `GET /modules/operations/{id}`, `GET /modules/{id}/secrets` (set or not, never the value) and `GET /modules/stream` (server-sent progress). The API only forwards to the module-manager and never holds the vault key or the Docker socket; the manager's refusals (`module_needs_choice`, `module_needs_confirmation`, `module_conflict`, `module_busy`…) keep their status and parameters, and an unreachable manager is `module_manager_unavailable`. All error codes are translated in French and English.
- The worker follows the installed modules (step 8): the module-manager exposes `GET /v1/connections` (running modules, in-network address, and only the secrets a manifest lists in the new `core_secrets` field), a `ProviderRegistry` maps a module to its adapter (Forgejo for `git`, Woodpecker for `ci`), and a `SchedulerSupervisor` rebuilds the scheduler when `platform_state.modules_generation` moves, swapping it between two ticks. If the manager is unreachable the running scheduler is kept; with no git/CI module installed the v0.1 pack files and the fake pack keep working. Jobs sent while no scheduler exists fail visibly with `scheduler_unavailable`.
- Module routes on the reverse proxy (step 9): `cobble_sdk.render_route` derives a Caddy route from the validated `web_ui` fields only (new `strip_prefix` field, default true), so nothing a module author writes freely reaches the proxy configuration. The module-manager publishes the routes of healthy modules validate-then-rename: files are written next to their final name, Caddy's admin API (a unix socket in a volume shared with the module-manager only) loads the whole Caddyfile, and the previous files are put back if Caddy refuses it. A refused route rolls an install back (`route_failed`, translated FR and EN); a proxy that cannot be updated never blocks a removal. A `caddy-init` one-shot gives the module-manager write access to the routes volume. The addresses given to the core use the real network alias (`cobble-<id>-<service>`).
- First catalogue module: `catalog/forgejo` (capability `git`), converted from the v0.1 pack. Its post-install hook creates the service account and the API token (handed to the vault, readable by the core only as `api_token`). Modules now receive `COBBLE_PUBLIC_URL` and `COBBLE_PUBLIC_HOST` (from `COBBLE_PUBLIC_URL` in `core/.env`), and hooks run with a minimal environment instead of inheriting the module-manager's own settings. `make dev-modules` starts the stack with the module-manager and `make smoke-modules` installs Forgejo through it for real, checks the token through Caddy, the absence of host ports and of leftovers after the uninstall. `backend/tests/unit/test_catalog.py` validates every catalogue module.
- Second catalogue module: `catalog/woodpecker` (capability `ci`, requires `git`), converted from the v0.1 pack with its docker-socket agent (declared as `host_access`, the only module that has it) and a gateway that lets pipeline containers reach the Git server at the public address. New platform mechanics for modules that require a capability: a `pre_up` hook runs before the module starts, once the provider runs (Woodpecker registers its OAuth application in Forgejo there and the platform hands the client id and secret to its compose file); hooks of a consumer receive the provider's address and the secrets the provider lists in the new `link_secrets` manifest field as `COBBLE_PEER_<CAPABILITY>_*` (never the core's or the browser's); finished init containers no longer count as unhealthy; `COBBLE_PUBLIC_PORT`, `COBBLE_GATEWAY_ALIAS` and `COBBLE_DOCKER_GID` join the platform variables, and `COBBLE_MODULE_EXTRA_ENV` (a JSON object of `COBBLE_*` strings) lets the operator add more (for example a CA bundle for pipeline steps). Module routes are imported before the v0.1 pack routes. `scripts/e2e_full.sh` now installs Forgejo and Woodpecker through the module-manager.
- Language-model backends (step 14): the manifest gains an `llm` block (where a backend listens and which models it serves, with a per-flavour override) and a flavour may bring its own compose file. The module-manager writes the models of the installed backends to a file the gateway includes (`include:` in `core/litellm/config.yaml`), restarts LiteLLM and waits for it to be healthy (the supported way in the pinned version: about 20 s); if the gateway does not come back, the previous list is put back and the install is rolled back (`llm_failed`, translated FR and EN). Hooks of a backend know their flavour (`COBBLE_VARIANT`) and what to fetch (`COBBLE_LLM_PULL`). Third catalogue module: `catalog/ollama` with CPU, NVIDIA and AMD (ROCm) flavours, the right one chosen from the machine's RAM and GPU, a small model on the CPU and a larger one with a GPU. The one-shot `caddy-init` became `volume-init` (it also prepares the model-list volume). New dev dependency: `types-pyyaml` (Apache-2.0).
- `cobble modules list | status | install | uninstall` (step 16): talks to the module-manager (never to Docker), shows the plan and asks before changing anything (`--yes` to skip, `--choose capability=module` when several modules can provide something, `--replace` for an exclusive provider), asks separately before removing modules that depend on what you remove, follows the operation to its end, and says where and why it failed and what was undone. Exit code 3 means the module-manager cannot be reached. Messages in French and English. The installer now makes the module-manager part of every install: it writes `MODULE_MANAGER_TOKEN` (kept across runs), `COBBLE_CATALOG_DIR`, `DOCKER_GID` and `COMPOSE_PROFILES=modules` to `.env` (existing installs gain them on `cobble update`; the derived values are refreshed in place), `cobble doctor` checks them (and a changed Docker socket group), and a v0.1 pack installed by hand is reported with how to move to modules, without touching it.
- The Store (step 17): a sidebar entry (administrators only) with a catalogue grid (search, category filter, state, and a module that does not fit this machine is greyed with the reason), a drawer per module (description in the interface language, license, what it provides and needs, flavour, a link to its web address, which secrets are set but never their values) and the install / removal flow: plan preview with what is added or removed automatically, a picker when several modules can provide a capability, a separate confirmation when removing a module removes others, live steps over the modules stream with a polling fallback so a dropped connection never hides the end, and the failure with its translated reason and what was rolled back. An operation goes on if the drawer is closed (a banner brings it back). The UI knows the module error codes (they used to show as "unknown error"). Playwright spec with the modules API mocked in the browser; a real run was driven in Chromium against a live module-manager (install with an automatically added dependency, cascade removal, dark mode, French).
- Starter packs (step 18, engine and CLI): `catalog/packs/*.yaml` (`local-gpu`, `local-cpu`, `api-only`) name a set of modules, the hardware they ask for and a priority. The SDK validates packs (`cobble_sdk.packs`, with a generated JSON Schema), checks them against the catalogue (unknown modules, or modules that would need a provider choice, make a pack unusable and are reported) and decides, as pure functions, whether a pack fits a machine (its own requirement and every module's) and which one to recommend (the fitting pack with the highest priority). The module-manager serves them (`GET /v1/packs`, also `GET /api/v1/modules/packs` for administrators), with fit, the recommendation and how much is already installed; `cobble modules packs` lists them and `cobble modules install --pack <id>` installs one (refused with the reasons if it does not fit). Installing a pack is an ordinary install of its modules, so rollback, cascades and progress are unchanged.
- Starter packs in the Store (step 18, UI): a "Starter packs" section above the catalogue, with the pack recommended for this machine marked, the others greyed with the reasons when they do not fit (a missing GPU, too little memory, naming the module that asks), a drawer per pack (its modules, how many are already installed) and an "Install this pack" button that runs the usual flow (plan preview, choices, live steps, rollback information) over all the pack's modules at once. If the packs cannot be read the catalogue still works.
- Model connections (the prerequisite of the first-run wizard and of the v0.1 step 11 validation): a v0.1 install could only ever talk to the built-in fake model (Settings had no key field, and `COBBLE_DEFAULT_MODEL` in `.env` never reached the containers). Administrators can now connect a model service with an API key (providers `openai`, `anthropic`, `openrouter`, or `custom` for any OpenAI-compatible address) through `GET/PUT/DELETE /api/v1/models`, test it (`POST /models/{name}/test`: the gateway's own health check, answered with a stable code such as `auth_failed`, never the provider's text) and make it the default (`POST /models/{name}/default`). The key is encrypted by the module-manager's vault (bound to the connection's name), is registered with the log redactor, is never returned by any route and is not in any log or event; the gateway receives it through its include file, a change is applied to the gateway first and saved only if the gateway accepted it, and the first connection becomes the default. The default is stored in the platform state and read at every call (`ModelPolicy`), so changing it needs no restart; roles pinned with `COBBLE_ROLE_MODELS` keep their model. Migration `0009`. ADR 0009 (proposed). The v0.1 release notes now say plainly that a real model could not be selected in v0.1 as shipped.

### Fixed
- `cobble doctor` no longer reports a one-shot container that finished successfully (such as `caddy-init`) as a failed container.
- Full real chain run end to end with the fake LLM (`make e2e-full`, PASS): `gen-env.sh` no longer fails on a first run; the backend image ships `git`; the runner image pre-warms a uv cache and a pnpm store with the template's dependencies and no longer leaks Aider's uv environment into project test runs; frontend tasks install dependencies before testing; a merge refused while Forgejo recomputes mergeability is retried after the pull request's mergeable flag settles; the `--comment` flow (new task `C-001`) also passes. The harness takes `E2E_HOST` and `E2E_BUILD_CA`.

### Added
- `scripts/step11_report.sh`: read-only report of the measurable rows of the step 11 validation table (models per role, duration, cost and tokens, escalations, failed/blocked tasks) from a running install.
- Repository skeleton: licenses (AGPL-3.0, Apache-2.0 for `templates/`), community files, issue and PR templates.
- Python tooling (uv, ruff, mypy strict, pytest), web tooling (pnpm, TypeScript, eslint, prettier, vitest), i18n key check, Makefile.
- GitHub Actions CI running lint and tests.
- Core stack (`core/compose.yml`): Postgres, Redis, LiteLLM, Caddy, API, worker and UI placeholder, images pinned by digest, only Caddy publishes a port. `make dev` starts it with no API key.
- Fake OpenAI-compatible LLM provider replaying cassettes (`providers/fake-llm`), with recording and automatic secret scrubbing.
- FastAPI app with `GET /api/v1/health`, Alembic with the `llm_calls` migration, Redis event bus, and a LiteLLM gateway that records tokens and cost per call.
- `make dev|dev-down|dev-logs|smoke|test-integration|cassettes`; CI job `core-stack` runs the full chain.
- Authentication: single admin created from a one-use activation link (`make activation-link`), scrypt passwords, hashed opaque sessions in an HttpOnly cookie, CSRF header, login rate limit. Folders and projects API (ADR 0003).
- React UI shell in the Open WebUI style: sidebar with project folders, top bar, chat area placeholder, settings dialog, System/Light/Dark theme from CSS tokens, FR/EN switch without reload. Lint rules reject literal UI strings and hard-coded colors; WCAG AA contrast of the tokens is tested.
- Capability interfaces (`LLMClient`, `GitProvider`, `CIProvider`, `AgentRunner`) with in-memory fakes, and a cost router that maps roles (`planner`, `test-writer`, `worker`, `reviewer`) to models and enforces a hard per-project budget: the project is paused and `budget.reached` is published at the cap (`budget.warning` at 80 %). Projects expose `budget_usd` and `status`.
- `python -m cobble.cli reset-admin`: new one-use link to set a new email and password without losing projects.
- Interview, spec and plan: per-project chat with the `planner` role (answers in the user's language), spec generation and approval, plan generation validated against a strict schema (every task has acceptance criteria and a size S or M; dependencies are acyclic), cost estimate shown before approval. Work runs in the worker; progress is pushed to the browser over server-sent events. Reference project `reference-projects/todo` and cassettes replay the whole flow.
- Installer (`installer/install.sh`) and `cobble` CLI (`status`, `logs`, `update`, `uninstall`, `doctor`, `reset-admin`), idempotent, FR/EN, with a CI matrix on Ubuntu 24.04/26.04 and Debian 12/13.
- Fixed pack (`packs/v01`): Forgejo and Woodpecker wired automatically, `ForgejoGit` and `WoodpeckerCI` providers, project template `templates/fastapi-react` with lint, tests, Semgrep, Trivy and Gitleaks; merge refused unless CI is green.
- Agent runner (Aider in a locked-down container, one per task) and `agent-service`, an egress allowlist proxy, and an internal LLM endpoint with signed per-run tokens so agent calls go through the cost router.
- Scheduler: tests-first runs (test-writer then worker), parallel only for independent tasks with disjoint files, loop detection, escalation, resume after a worker restart.
- Milestone demos: build, tag and preview per milestone, validate, comment (becomes a task) or revert to the previous milestone. Preview service for real previews; fake pack mode for development and CI.
- Agents tab (live logs, diff, pause/resume/stop/retry), Demo tab and Costs tab (USD and tokens by task, model and role).
- Public documentation is English-first (README, wiki, release notes, CONTRIBUTING, SECURITY) with a French version below each; wiki pages renamed in English.
- README with screenshots (`make screenshots` regenerates them), bilingual wiki sources in `docs/wiki` and `scripts/publish_wiki.sh`.
- `make e2e` (Playwright) against the full stack; CI job `e2e`.
- i18n key check now also covers backend (`backend/cobble/locales`) messages.
