# v0.2 spikes — findings (PR 0)

Date: 2026-11-01. Findings only: no feature code. Measured in a development sandbox (4 vCPU, warm
Docker cache, images pinned as in `main` at `b8d91f4`). These inform ADR 0008 (still a draft).

## 1. Caddy: admin API on a unix socket, fragments, fail-safe reload

Setup: pinned `caddy:2-alpine`, `admin unix//run/caddy-admin/admin.sock`, site block with
`import /etc/caddy/frag/*.caddy`, socket volume shared only with the controlling process.

| Check | Result |
|---|---|
| Add a fragment, `caddy reload --address unix//…/admin.sock` | works, route live at once |
| Remove a fragment, reload | works, route gone |
| Admin API over TCP from the host (`localhost:2019`) | unreachable (good: only the socket volume) |
| Reload with a **broken** fragment (unknown directive) | exit 1 with a precise message (file and line); **previous routes keep serving** |
| Fragment with an unreachable upstream | reload succeeds; requests answer 502 at request time |
| **Restart** Caddy while a broken fragment is on disk | **Caddy does not start** (container exits) |

Consequences for the design:
- The manager must **validate before writing into the live folder**: write the fragment to a temp
  directory, run `caddy adapt` / `caddy validate` on the full tree, then rename; delete on failure.
  A bad fragment must never reach the directory Caddy reads at boot.
- A health check for a module's upstream is a separate concern from the reload (a 502 is not a reload error).
- Unmatched paths answer **200 with an empty body**: tests must compare bodies, not status codes.
- **Routing by path is already proven**: v0.1 serves Forgejo under `/git/` and Woodpecker under
  `/ci/` and `scripts/e2e_full.sh` passes with it. PLAN.md §6 allows "path or sub-domain", so
  **per-module hostnames are not required for v0.2**. Keep path prefixes (`/<id>/`) and drop the
  hostname/wildcard-DNS risk. (Not tested here: a *new* module under an arbitrary prefix; each
  product must support a base path, as Forgejo `ROOT_URL` and Woodpecker `WOODPECKER_HOST` do.)

## 2. LiteLLM + Ollama (pinned `v1.106.6`)

Setup: config with `model: ollama_chat/qwen2.5-coder:1.5b`, `api_base: os.environ/OLLAMA_API_BASE`
pointing to a host that does not exist.

| Check | Result |
|---|---|
| Starts with the Ollama backend unreachable | yes, `/health/liveliness` answers |
| `os.environ/…` reference for `api_base` | works |
| `/v1/models` lists the entry | yes |
| Call while the backend is down | clean `500` `APIConnectionError` message, no crash |
| Warning for a model absent from the bundled cost map | only a log warning when custom prices are set (set `0`/`0`) |
| Cold start to live | 42.7 s |
| `docker restart` to live | 20.3 s |

Decision supported: **regenerate `config.yaml` and restart LiteLLM** (no `STORE_MODEL_IN_DB`, no
database). Consequences:
- A restart is ~20 s: the core's clients (API, worker) must retry on connection errors during a link
  or unlink, and the manager should wait for `/health/liveliness` before declaring the link done.
- The Ollama module can be installed before the model is pulled; a request then fails cleanly and
  the `on-link` hook pulls the model afterwards.
- Not verified: a real Ollama server and model (none available in the sandbox), GPU variants.

## 3. Forgejo + Woodpecker link: headless and idempotent

`packs/v01/hooks/install.sh` run twice in an isolated compose project (`spikelink`, own env files):

| Run | Result |
|---|---|
| First install (images cached) | rc 0, **39 s**: Forgejo, service account, token, OAuth app, Woodpecker, Woodpecker token, `.env.pack` |
| Second run | rc 0, **3 s**, a no-op |
| State after the second run | same 17 + 5 keys; **no key added, removed or changed** (compared without printing values) |

So the existing link is headless and idempotent. The reverse order is not a separate scenario:
Woodpecker `requires: [git]`, so the planner installs a git provider first (decision 3 of the v0.2
plan). Not covered by the current hooks and still to design: `on-unlink` (today `unlink.sh` only
deletes `.env.pack`), uninstalling Forgejo while Woodpecker exists (cascade plan), and relinking
after a provider replacement.

## 4. Compose rewriter

`docker compose config --format json` renders all three pack files **without a Docker daemon**, so
the rewriter can be a pure function over that JSON (tested with golden files).

What the rules would have to change:
- **Project names:** `cobble-pack`, `cobble-pack-agents`, `cobble-pack-preview` → `cobble-<id>`.
- **Fixed names:** networks `cobble_agents`, `cobble_previews`, `cobble-pack-ci`, `cobble-pack-internal`; volumes `cobble_agents_data`, `cobble_previews_data` (not namespaced); the shared external `cobble_core` network is joined by forgejo, woodpecker-server, agent-proxy, agent-service and preview-service.
- **Docker socket** (3 services): `woodpecker-agent`, `agent-service`, `preview-service` → the documented `host_access: docker_socket` exception.
- **Bind mounts:** `pack-gateway` mounts two files from `packs/v01/caddy`; `agent-service`/`preview-service` mount the socket. No host ports are published (good).
- **Images:** 5 pinned by digest (forgejo, caddy, alpine, 2 woodpecker); 4 built locally (below).
- `pack-gateway` exists only to give pipeline steps a stable public URL; it overlaps with the core Caddy routes and needs its own design.

## 5. First-party images and digest pinning

| Image | Size | Base |
|---|---|---|
| `cobble-agent-proxy` | 12 MB | alpine, pinned |
| `cobble-agent-service` | 432 MB | python-slim + uv, pinned |
| `cobble-preview-service` | 432 MB | python-slim + uv, pinned |
| `cobble-aider-runner` | 2,248 MB | node + python, pinned; includes the pre-warmed uv cache and pnpm store |

All bases are digest-pinned already; only the images Cobble builds itself lack a digest. Findings:
- ~3.1 GB of first-party images must come from somewhere. Building on the user's machine keeps the
  pins meaningful only through the base digests and the lock files, and takes minutes; publishing
  them from CI (a registry such as GHCR) gives real digests for `catalog/lock.yaml` and faster,
  offline-friendlier installs but adds a publishing pipeline and storage.
- Not tested here (no registry access): pushing from CI and pinning by digest. Measured instead:
  install and relink of the Forgejo+Woodpecker pair takes ~40 s with warm images, so an any-order
  matrix over only the two link pairs is affordable in CI; a full matrix of all modules is not.
- The runner's size comes from Aider, Node and the template caches: worth reviewing before it is
  published (a multi-gigabyte image per release).

## Summary for ADR 0008
1. Caddy: unix-socket admin, **validate-then-rename** fragments, path prefixes (no hostnames).
2. LiteLLM: **regenerate config and restart** (~20 s), clients retry, wait for liveness.
3. Forgejo↔Woodpecker link is already idempotent; design `on-unlink` and the cascade.
4. The compose rewriter works on `compose config --format json`; list of renames above.
5. Decide between building images on the host and publishing digests from CI before PR 10.
